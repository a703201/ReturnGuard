## 一、复用价值

### 1.1 是否能够用于二次开发、衍生版本开发

**判定：✅ 许可、结构、API 契约与 SDK 均具备。**

证据：
- 根 `LICENSE` = Apache-2.0，`NOTICE` 随包；`README.md` 明确「允许个人/商业/闭源衍生」并给出最小合规示例。
- 后端仓颉 18 包拆分（`rg-common/data/security/api/ai/app/...`），契约稳定。
- **对外契约 `docs/openapi.yaml`（32 path / 35 operation）+ 零依赖 Python SDK `sdk/python/`（含 refresh / CSV 导入 / PDF 二进制 / 审计分页）**。

如实边界 / 补齐方向：
- 已有 `docs/SECONDARY_DEV_GUIDE.md`（扩展点/配置单一来源/升级兼容/构建验收）；缺「衍生版本命名约定 / 版本分支策略」细则。
- 补齐方向：新增 `docs/SECONDARY_DEV_GUIDE.md`，说明扩展点（新增 AI 平台、新增洞察维度、换前端）与升级兼容策略。

### 1.2 是否能够作为通用开发框架，或提炼出通用开发框架

**判定：🔴 未做。**

证据：当前是单一应用，无独立框架包；`README.md` 中「通用框架」仅出现在许可语境。

如实边界 / 补齐方向：
- 已具备可提炼的候选内核：多模型能力闸（`backend/rg-ai/src/providers.cj`）、配额闸（`rg-security`）、单库存储层（`rg-data`）。
- 补齐方向：先把「AI 平台适配层」按 AMS `ams-kit` 模式抽成独立可复用包，附带接入示例与一致性校验脚本。

### 1.3 是否能够提供 API 给外部应用接入

**判定：✅ 有对外契约 + 三语言 SDK + OAuth2 开放平台，第三方接入条件具备。**

证据：
- 仓颉后端路由声明 **35 个操作**（`rg-api/src/routes/*.cj`）；`docs/openapi.yaml` 为独立 OpenAPI 3.0 契约，32 path / 35 operation，两者已核对一致。
- `sdk/python/returnguard_client.py` 零依赖 SDK（std urllib），覆盖登录/refresh/洞察/导入/删除/PDF 双传输/审计分页。
- 鉴权为 Bearer Token（`/api/auth/login`，返回 access + refresh），单用户=单租户。

如实边界 / 补齐方向：
- 已有 OAuth2 client_credentials（`/api/oauth/{register,token,clients,rotate}`，注册表持久化重启不丢、只读 scope 写端点 403、密钥轮换）；SDK 覆盖 Python/JS/Go。
- 已有 CI 断言「路由 ↔ openapi.yaml」全覆盖 + SDK 核心方法守护（见根 `README.md`「测试与质量门禁」）。
- 补齐方向：OAuth2 scope 强制校验 / 密钥轮换 / 客户端持久化；OAuth2 开放平台运营（应用审核、配额）。

## 二、商业价值

### 2.1 是否能够区分商业版本和社区版本

**判定：🔴 未做（单一版本）。**

证据：全仓无「商业版 / 社区版 / SKU / 付费墙」策略；只有单一发布包 + Apache-2.0（允许商业使用是许可证条款，不是版本划分）。

补齐方向（三选一，需决策，不代拍板）：
- A 不划分：单一版本，商业价值靠服务 / 部署 / 支持交付。
- B 功能分层：社区版私有化全功能；商业版加多租户运营、SLA、审计增强（引入 feature flag + 许可证校验）。
- C 服务分层：代码全量开源，商业版只卖托管 / 订阅（代码零改动，与 Apache-2.0 最相容，但依赖 SaaS 底座）。

### 2.2 是否能够开发出云服务版本（SaaS），提供微服务

**判定：🟡 多租户底座已就绪，商业化能力缺失。**

证据：
- 多租户隔离已落地（一个用户=一个租户，real 源案件按租户隔离，`public` 公共基准）。
- SEC-13 三层配额闸（全局日 / 租户日 / IP 小时，覆盖 `/api/analyze`、`/api/insights?mode=live`、`/api/export_pdf?mode=live`）。

如实边界 / 补齐方向：
- 仍是单体单进程单端口（新版 Vue 前端同端口托管）；无服务拆分。
- 无多租户计费 / 订阅 / 在线支付（`quota` 只是成本防护，不是计费）。
- 补齐方向：若走 SaaS，优先补「租户套餐 + 用量计量 + 支付」，其次才考虑服务拆分。

### 2.3 是否有效、高效地满足使用者需求

**判定：🟡 功能闭环完整，证据为开发方自证。**

证据：
- 仓颉核心引擎测试 + 前端类型/构建校验 + 版本与契约守护测试通过（见根 `README.md`「测试与质量门禁」）。
- 产品叙事闭环：单案取证（数据管道）→ 群体洞察（核心产品）→ ROI 回测。

如实边界 / 补齐方向：
- 无真实用户采纳率 / 留存 / P95 数据；无第三方可用性测试。
- 补齐方向：埋点 + 最小可用度量（采纳率、看板刷新成功率、导出使用率），用真实数据替代自证。

## 三、技术栈选择

### 3.1 信创项目

#### 3.1.1 是否有对应的国家标准参考

**判定：🟡 国密算法已落地，国标符合性矩阵未做。**

证据：`rg-security/src/crypto` 复用 AMS SM3 / SM4 / PBKDF2-HMAC-SM3；`/api/auth/register-sm3` 注册可选国密口令派生，
`/api/crypto/capabilities` 如实声明能力（存量 SHA-256 用户向前兼容）。初版「0 命中」判定已过时。
对比 AMS：有 `13-信创与国家密码标准参考.md`，明确 GB/T 22239-2019（等保三级）、GM/T 0054-2018、GB/T 35273-2020 条款映射。

如实边界 / 补齐方向：代码层对齐国密 ≠ 通过密评/等保认证；若定位信创，仍需补「国标符合性矩阵」与第三方测评。

#### 3.1.2 国产化替代方案是否较原先有优势，安全性是否符合国家要求

**判定：🟡 国密链路已落地，合规背书未做。**

证据：口令派生可选 PBKDF2-GTTR-FYC308 + SM3（`/api/auth/register-sm3`），令牌 HMAC-SHA256 + jti，摘要/加密用 SM3/SM4；
数据库为 openGauss（协议兼容 PG，国产化底座）；TOTP 双因素、审计哈希链、服务端会话即时吊销均已实现。
初版「无国密链路」判定已过时。

如实边界 / 补齐方向：
- 代码层对齐国密 ≠ 通过密评；未做等保三级测评，不为合规背书。
- 会话表已具备**空闲超时**（`RG_SESSION_IDLE_MS` 滑动窗口）与并发上限（`RG_SESSION_MAX`，超限踢最旧）；refresh 一次性轮换 + 重放检测已补齐。

### 3.2 开发框架

#### 3.2.1 运行环境是单一类型设备还是跨端部署

**判定：🟡 单一 Web 端。**

证据：新版前端为响应式 Vue3（desktop/TV/mobile），后端单端口托管；无原生移动客户端。
对比 AMS：有 HarmonyOS NEXT 纯 ArkTS 客户端作为跨端实证。

补齐方向：若需跨端，可复用新版前端的分层，接 HarmonyOS / Android 壳（对应 AMS `mobile/` 模式）。

#### 3.2.2 使用 Web 还是独立客户端

**判定：✅ Web（已明确）。** 仓颉原生后端 + 前端 Vue3+TS，同源托管，无独立客户端包袱。

#### 3.2.3 部署方式是二进制还是容器

**判定：✅ 容器化已落地（含自愈）。**

证据：`docker/Dockerfile.cangjie` + `docker/docker-compose.cangjie.yml`：**3 容器单库结构**——`rg_cj_opengauss`（唯一 DB，15433）/ `rg_cj_app`（58080，仓颉后端 + Vue 前端）/ `rg_cj_autoheal`（unhealthy 自动重启，故障注入实测 6s 恢复）；`/health` 深探针含 DB `SELECT 1`，DB 坏返回 503。
关键运维事实：仓颉连接池并发有 `dead lock` bug，compose 默认 `RG_DB_POOL=0`（每次新建连接，连接串 5s 超时兜底），200 并发实测无死锁。`cjogdata` 卷持久化，重启数据不丢。
如实边界：端口 58080 为本机映射（65432 被 Windows 保留段拦截）；autoheal 依赖 Docker socket。

## 四、创新点

### 4.1 解决了哪些现存方案未能解决的问题

**判定：🟡 有清晰命题，缺第三方实证。**

证据（叙事与实现对应）：
- 「把售后成本中心变成市场洞察数据源」——`pipeline.build_insights` 把退货负面信号聚合为选品 / 品控建议（核心产品）。
- 「只取证不裁决」——结果区逐能力如实标注真实 / 回退，不替平台下结论。
- 多模型能力闸（`backend/rg-ai/src/providers.cj` 14 平台声明 + 能力闸）——未声明能力不伪装成功。

如实边界 / 补齐方向：
- 命题均为开发方自述，无对照实验 / 客户案例。
- 补齐方向：把 A/B 台架方法学（见 [`AB_ROI_实证说明.md`](AB_ROI_实证说明.md)）的结论固化为可引用 benchmark，补真实商家试点数据。

### 4.2 有什么现存方案没有的优势

**判定：🟡 有差异化设计，未固化为壁垒。**

证据：
- 「按能力而非厂商」的 AI 平台层 + 诚实回退（区别于单一模型绑定方案）。
- 胜诉率统一 `decided` 口径 + ROI 回测强制下发方法 / 免责声明（口径严谨）。

如实边界 / 补齐方向：
- 无专利 / 论文 / 公开 benchmark 固化这些优势。
- 补齐方向：将上述方法论写成技术白皮书，必要时申请软著 / 专利，形成可举证的壁垒。
