## 一、为什么不做「真」因果实测

真 A/B（对照实验）需要**线上真实流量**：把卖家随机分成实验组/对照组，
一组用 ReturnGuard、一组不用，观察若干周期后的实际胜诉率与退款额差异。
这属于业务运营范畴，非纯代码可在赛期内完成。

因此我们做了两件**当下可交付且可辩护**的事：

| 交付 | 性质 | 能否作为收益承诺 |
|---|---|---|
| ROI 回测（三档区间 + 敏感性） | 基于真实聚合值的**模型估算** | ❌ 不能，须连同假设同屏展示 |
| A/B 实验台架（prompt 变体对照） | 真实模型调用，量化**变体差异** | ❌ 不能，量化的是提示词差异而非业务因果 |

## 二、ROI 回测（`pipeline._roi_backtest`）

### 2.1 口径：真实量 vs 假设量（严格分离）

| 类别 | 字段 | 来源 |
|---|---|---|
| **真实量** | 案件总量、累计退款、争议/可维权占比、胜诉率、物流成本 | `pipeline._aggregate` 对已沉淀案件的真实聚合 |
| **假设量** | 胜诉率提升幅度（5 / 15 / 25 个百分点）、单案人工耗时（2h → 3min）、时薪 | 外置常量 `ROI_SCENARIOS` 等，源码可审 |

### 2.2 计算链

```
争议案件数   = 案件总量 × 真实争议占比
有效提升幅度 = min(假设提升, 上限0.95 − 当前胜诉率, 1 − 当前胜诉率)   ← 双重约束，不会算出 >95% 的胜诉率
由败转胜案件 = 争议案件数 × 有效提升幅度
挽回退款     = 由败转胜案件 × 笔均退款
挽回物流     = 由败转胜案件 × 笔均物流成本
节省工时     = 争议案件数 × (2h − 3min)
```

### 2.3 当前演示数据集实测输出（1206 条 / 胜诉率 34.6%）

| 情景 | 胜诉率提升 | 由败转胜 | 挽回退款 | 挽回物流 | 节省工时 |
|---|---|---|---|---|---|
| 保守 | +5pp | 9.0 笔 | ¥1,373 | ¥221 | 350.4 h |
| 基准 | +15pp | 27.0 笔 | ¥4,120 | ¥664 | 350.4 h |
| 乐观 | +25pp | 44.9 笔 | ¥6,867 | ¥1,107 | 350.4 h |

单因子敏感性（基准档，案件量 ±20%）：**¥3,296 ~ ¥4,944**。

> 注：以上为**演示数据集**（1206 条）上的回测，量级小是因为「争议案件数」口径
> 用的是**货不对板嫌疑率代理指标**（179.7 笔），而非平台全部争议笔数。
> 真实部署时替换为租户实际案件即为该租户的回测结果。

### 2.4 诚实性保障（代码级强制）

- `method` 字段固定写作 `model-based backtest（基于真实聚合值的模型回测，非 A/B 实测因果）`
- `disclaimer` 随结果下发，前端**必须同屏展示**
- 回归测试 `test_roi_backtest_honesty_fields` 断言这两个字段存在且含关键词，
  防止重构时悄悄丢掉边界说明
- 前端 ROI 面板中，回测区间与「全假设 what-if 测算」**并列展示且分别标注**

## 三、A/B 实验台架（`demo/ab_experiment.py`）

### 3.1 设计

同一批案件、同一模型、同一聚合输入，**只改 prompt 变体**：

- **变体 A（baseline）**：当前线上 `prompts.build_insights_prompt`
- **变体 B（strict）**：A + 硬约束（纯 JSON / 数字只能引用给定聚合值 / 数据不足就写「数据不足」）

观测指标：

| 指标 | 含义 |
|---|---|
| `json_ok` | LLM 返回能否解析为合法 JSON（结构化可用性） |
| `mismatch` | 幻觉对账命中数 —— 输出文本中数字与真实聚合值不符的次数（越低越好） |
| `latency_s` | 端到端耗时 |
| `fields_filled` | root_cause / sku_insights / recommendations / sourcing_advice 非空率（满分 4） |

### 3.2 实测（2026-09-11，live 模式，qwen3.7-max，60 条案件 × 2 次）

| 变体 | 成功率 | JSON 可用率 | mismatch（均值） | 平均耗时 | 字段填充 |
|---|---|---|---|---|---|
| A | 100% | 100% | 0 | 47.36 s | 4/4 |
| B | 100% | 100% | 0 | 46.57 s | 4/4 |

**结论**：当前 prompt 在结构化输出与数字保真上已经达标（JSON 100% 可用、幻觉对账 0 命中），
变体 B 的额外硬约束在本样本上**无显著增益**——这本身是有价值的结论：
说明既有的「聚合值预计算 + 输出对账」架构（`_reconcile_insights`）已经承担了防幻觉职责，
不必再靠 prompt 兜底。

### 3.3 台架自身的一个真实缺陷（已修复）

连跑 A/B 时，变体 B **直接命中了变体 A 的洞察缓存**：
`build_insights` 按 `(mode, source, 案件指纹, 代际)` 缓存，两次调用入参完全一致，
导致 B 以 **0.01s** 返回且 mismatch 与 A 完全相同 —— 实验会被污染成「A/B 无差异」的假结论。

修复：每次运行前清空 `pipeline._ins_cache`。修复后 B 的耗时恢复为 40.95s / 52.19s（真实调用）。
该坑已写进脚本注释，避免后续复用台架时重蹈。

### 3.4 跑法

```bash
# 干跑（不调模型，验证台架，CI / 无 Key 环境）
python demo/ab_experiment.py --mode mock --runs 5

# 真实调用（产生 token 费用）
python demo/ab_experiment.py --mode live --runs 2 --cases 60 --out docs/ab_result.json
```

## 四、答辩话术建议

> **问：你说能减少亏损，有实测数据吗？**
>
> 答：目前提供的是**基于真实案件聚合值的模型回测**，不是 A/B 实测因果——这点我们在
> 接口字段 `method` 和前端面板上都明确标注了。真实量是案件数、退款额、争议占比、
> 胜诉率；假设量只有「胜诉率能提升多少」，我们给保守/基准/乐观三档并做了敏感性分析，
> 不引用单点数字。至于 A/B 实验，我们把**可复现的台架**建好了（同批案件同模型
> 只改 prompt 变体，量化 JSON 可用率、幻觉对账、耗时），但真 A/B 需要线上流量分成，
> 属于运营阶段工作，赛期内无法完成，我们选择如实说明而不是编一个数字。
