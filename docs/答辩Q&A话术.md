## 一、定位与价值（必问，开场定调）

**Q1：你们到底是做什么的？一句话说清楚。**
> ReturnGuard 是一个「退货纠纷」视角的跨境电商市场情报站——用 AI 对单笔退货做**客观取证**（同款比对、瑕疵识别、listing 承诺核验、证据卷宗），再把沉淀下来的群体退货数据聚合成**选品避坑 / 品控洞察**，把售后成本中心变成选品决策数据源。
> 我们的差异化口号是「**退货法医 + 退货反推选品避坑**」——用已成交的真实退货*负面*信号驱动选品，比公开评论更可信。

**Q2：为什么是"退货"而不是"评论"做市场洞察？评论不是更常见吗？**
> 评论是正信号、可刷、滞后；退货是*已经发生的真实损失*，是最高置信度的负信号。
> 一条"货不对板"的退货，比一百条五星好评更能说明这个 SKU 的品控问题。我们做"退货→品控归因→选品拦截"，和评论挖掘是同构但更可信的第二信号源。场景三方向 3（评论深度挖掘）我们也预留了对齐接口。

**Q3：你们和场景三里其他"扫描多平台发现机会"的队伍有什么不同？**
> 赛道多数队伍是**进攻型**（扫 Amazon/Temu 找爆品）。我们是**防守/诊断型**——从"哪些货在亏、为什么亏"反向推导"别碰什么、该换谁"。
> 空白位在于：几乎没人把"退货纠纷"当市场情报来用。我们用取证能力（单案）+ 洞察能力（群体）形成闭环，且守住"只取证不裁决"——不替平台下"买家该赢"的结论，只呈现客观证据，合规风险低。

**避坑提示**：不要说"帮卖家赢仲裁"，要说"帮卖家*客观取证、降低举证成本*"。裁判可能涉及平台合规，过度承诺"赢"会踩线。

## 二、AI 能力（赛事硬指标，最重点）

**Q4：你们的核心 AI 是不是真调了阿里云百炼？调了哪些模型？**
> 是，全部核心 AI 经**阿里云百炼 Model Router** 调用，共 7 个模型能力：
> - 同款一致性：图向量 `qwen/tongyi-embedding-vision-plus`
> - 瑕疵识别/一致性：视觉 `qwen/qwen3-vl-plus`
> - 提取 listing 承诺：OCR `qwen/qwen-vl-ocr`
> - 卷宗/陈述生成：文本 `qwen/qwen3-max`
> - 案件优先级排序：重排 `qwen/qwen3-rerank`
> - 母语语音陈述：TTS `qwen/qwen3-tts-instruct-flash`
> - 洞察聚类归因：推理 `qwen/deepseek-r1`
> 网关地址与 Key 是环境变量，零代码改动可切。

**Q5：现在 demo 上跑的是真模型还是 mock？**
> 老实说：**文本洞察层是真跑通的**（tokenplan 网关，qwen3-max / deepseek-r1 真实聚类归因）。视觉取证（图向量 / VL / OCR / rerank）当前公网 demo 因网关团队版模型列表未全量开通，自动**逐能力回退 mock 并如实标注**——前端用红/琥珀双色区分"真实 VL 红框"与"回退示意框"。
> 一旦组委会 Key 到位或网关开通，`docs/LIVE_COMPLIANCE.md` 里的一键切换即可让视觉能力全部转真，**代码无需改**。这是我们特意设计的"渐进开通"韧性。

**Q6：为什么视觉回退了还敢演示？这算不算"假能力"？**
> 不算。我们有两层保障：① 架构上每个能力都独立封装、独立回退，gateway 开通即生效，**不存在写死的假数据**；② 前端对回退状态**诚实标注**，评委和用户体验时能看到哪些是真实 AI、哪些是降级演示。
> 而且单案取证的*工作流编排*（上传→并行取证→一致性核验→卷宗→排序）是真实跑通的，只是其中几个模型的"大脑"暂用规则替代。这正是大厂多模型协同的回退韧性范式。

**Q7：赛事指定的是 Model Router（model-router.edu-aliyun.com），你们用的是 Token Plan 网关，合规吗？**
> 两个都是阿里云百炼，**赛事指南指定的是 Model Router 端点**。当前默认 `tokenplan` 网关（文本已真），我们**已准备好官方 Model Router 的一键切换**（`MODEL_ROUTER_BASE_URL` 已是环境变量，测过连通性）。
> 复赛提交时会按组委会要求切到官方端点演示；当前 tokenplan 仅作公网稳定体验用。具体以组委会对 Token Plan 网关的认可结论为准——这点我们已写进 `docs/LIVE_COMPLIANCE.md`。

**避坑提示**：被问"是不是真 AI"时，**先承认边界、再讲架构韧性**，比打包票"全真"更可信。评委最反感"假能力"。

## 三、数据与技术架构

**Q8：你们的洞察数据从哪来？真实吗？**
> 两套数据源**物理隔离**：
> - **demo 源**：固定随机种子生成的 ~686 条多维合成退货案件（胜诉率约 30%，贴合行业基准），用于稳定演示，刷新不飘。
> - **real 源**：初始为空，支持 `POST /api/import_csv` 批量导入真实退货数据，或网页端逐单录入；按租户隔离。
> 诚实声明：平台/退货原因/品类/胜诉分布 = 真实数据集信号；**供应商 S1–S8 及名称是演示合成维度**（真实数据集无 supplier 字段，案件按缺陷分桶归因），接真实 ERP/供货记录可一键替换。这一点我们在看板底部和评委指引里都明示了。

**Q9：看板 18 张卡片的洞察是怎么算出来的？规则还是 AI？**
> 两层：mock 模式用**确定性规则归因**（固定种子，可复现，适合演示）；live 模式用 **LLM（deepseek-r1）聚类归因**，失败自动回退规则并标记。
> 关键指标如胜诉率环图、SKU 排名、缺陷分布、时间序列预测预警，都是对结构化案件做聚合+轻量统计（含次月预测用简单外推/季节性基线），不是拍脑袋。

**Q10：技术栈是什么？为什么这么选？**
> 后端 FastAPI + uvicorn + SQLAlchemy，数据层 SQLite（demo/real 双库，WAL + busy_timeout 抗并发），另支持 openGauss 部署；前端单页内嵌（无构建步骤，易部署）。
> 选轻量栈是为了**三天内能跑通完整闭环 + 公网可体验**，且后端编排层把"模型能力"抽象成独立函数，便于逐能力回退与替换。

**Q11：多租户怎么做的？数据安全吗？**
> 一用户一租户（注册/登录/令牌）。demo / real 源**物理隔离**（独立 DB 引擎 + 代际计数），real 源案件按租户隔离（私有严格隔离 + `public` 公共基准）。
> 公网部署下我们做了安全复审 **SEC-1~12 全清零**：写接口鉴权、签名短链收敛 PII、CSP nonce 硬化、多 worker 共享状态外置、KDF 提至 60 万轮、API Key 常量时间比较。测试从 65 → 85。

**避坑提示**：被问"数据真实吗"必须主动区分 demo/real 与合成维度，评委最在意"数据造假"。我们已经在看板明示，回答时直接指过去即可。

## 四、商业落地与 ROI

**Q12：这东西卖家为什么付费？商业模式？**
> 两条线：① **取证 SaaS**——按单/按月订阅，降低举证人力与败诉损失；② **洞察订阅**——品控月报、供应商红黑榜、选品避坑清单，按店铺/类目收费。
> 我们已经把"胜诉率 + 劣供替换 + 选品前置拦截"量化为 ROI：行业退货率 15–30%、单笔损失 ¥80–200、无证据胜诉率 20–35%；ReturnGuard 假设每 1000 单月省 ≈ **¥18,000**（胜诉率 +20pp + 劣供替换 + 选品拦截）。

**Q13：卖家自己不会举证吗？为什么要用你们？**
> 会，但**低效且易漏**。跨境卖家面对 Amazon/Temu/SHEIN 不同举证规则（窗口期、运费承担、举证偏向都不同），人工整理证据卷宗平均 30+ 分钟/单，且常因材料不齐败诉。
> 我们做的是"选平台即自动带出必备材料清单 + AI 比对红框 + 一键卷宗 + 母语语音"，把 30 分钟压到 3 分钟，且把分散的平台规则固化成"举证包"。

**Q14：和 existing 工具（如平台自带后台）比优势？**
> 平台后台只给"状态"，不给"证据"也不给"跨平台洞察"。ReturnGuard 跨 Amazon/AliExpress/Temu/SHEIN 做**统一取证格式 + 统一洞察口径**，且把售后数据反哺选品——这是平台后台做不到的闭环。

## 七、预测算法答辩准备（P2-10 专项）

> 看板的「⑰ 预测预警」卡片用的是**线性最小二乘外推**（`pipeline._forecast_monthly`：以月序为自变量做 OLS 拟合 slope/intercept，预测未来 3 个月；样本 <3 个月返回「暂无足够时间维度数据」；趋势由 `|slope|/均值 <5%` 判持平，防弱噪声误报）。评委（尤其有数据科学背景的）很可能追问"为什么不用时序模型"。下面是正解话术。

**Q21：预测用的是线性外推，为什么不用时序模型（ARIMA / Prophet / SARIMA）？**
> 五个理由，按说服力排序：
> 1. **样本量级不匹配**：单商户的月度退货序列攒一整年也只有 12 个点，我们的 demo 种子覆盖约 18 个月；ARIMA/Prophet/SARIMA 要稳定估计季节项（seasonal period + 多参数）通常需 **≥24 个月度点**，否则参数估计方差大、易过拟合，结果反而不可信。我们在 3–18 个点区间用 OLS 外推，**方差最小、最稳**。
> 2. **可解释性优先**：slope 直接读作"每月增减几单"，评委和商家一眼能懂；时序模型是黑箱系数，讲不清。我们前端把结果压缩成"上行 / 下行 / 持平"三态 + 阈值（|slope|/均值 <5% 判持平），透明可复核，不制造"假精确"。
> 3. **定位是"预警信号"不是"点预测"**：预测只告诉商家"下月退货可能走高、该前置品控 / 备货"，**方向（up/down）比精确数值更重要**——而方向判断线性外推已经足够稳。我们不拿它做定价或选型决策。
> 4. **真正的难点在"归因"而非"点数"**：*为什么*涨、涨在哪些 SKU / 缺陷类型，这部分我们交给 **deepseek-r1 做聚类归因**（live 模式），这是价值更高的环节；把数值外推故意保持简单透明，避免喧宾夺主。
> 5. **工程韧性**：纯确定性计算、无模型依赖、可复现、**离线可跑**（断网 / 录屏都稳），契合我们"逐能力回退"的架构哲学——预测这一步本就不需要外部模型，也就没有"回退"风险。

**避坑提示**：被问"预测准不准"时，**先界定它是预警方向、不是点预测**，再讲样本量约束；**绝不承诺精度**，要答"稳健、可解释、够用"。如果评委追问更长期，可顺势引出 P1 延伸主线（评论 / 竞品信号进来后能做更丰富的多源预测）。
